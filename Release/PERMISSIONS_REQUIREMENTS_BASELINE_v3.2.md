# PinChat 官方式权限需求基线 v3.2（冻结）

状态：已确认、实施中、冻结  
确认日期：2026-09-16  
适用范围：PinChat 发起及继续的本机 Codex 任务权限、审批与权限提示

## 1. 冻结规则

本文件只记录 v3.2 新增范围，不修改 v1.0 至 v3.1 的冻结基线。生成 SHA-256 校验并设为只读后不得原地修改；后续变更必须建立更高版本基线。

## 2. 核心目标

- PinChat 不再把所有任务固定为 `read-only + never`，权限行为应尽可能接近本机官方 Codex 桌宠。
- 权限代表任务可以使用的能力上限，不构成强制工具调用；普通知识问答不得因为启用较高权限而被要求读取文件或扫描磁盘。
- 默认使用兼顾实用性和安全性的“询问批准”，同时提供“自动批准”和“完全访问”供用户明确选择。
- 不接 OpenAI API；继续使用本机 Codex App Server、ChatGPT 登录和用户现有额度。

## 3. 权限档位

- 询问批准：`approvalPolicy = on-request`、`approvalsReviewer = user`、`sandbox = workspace-write`。
- 自动批准：`approvalPolicy = on-request`、`approvalsReviewer = auto_review`、`sandbox = workspace-write`；仅符合 Codex 自动审查条件的请求可自动决定，严格请求仍交由用户。
- 完全访问：`approvalPolicy = never`、`sandbox = danger-full-access`；不使用 Codex 文件与网络沙箱，但仍受 macOS TCC、完全磁盘访问、系统安全窗口和其他操作系统保护约束。
- 用户选择持久化；新建线程、恢复线程和交接前的线程恢复均使用当前所选档位。进行中的单次操作不因设置切换而被静默重写。

## 4. 权限交互

- 输入条应提供紧凑权限入口，设置页应展示三个档位、当前档位说明和完全访问风险提示。
- App Server 发出命令执行、文件变更或权限扩展审批时，PinChat 必须识别真实请求 ID 和任务信息，自动展开回答小窗并展示原因、命令或路径。
- 用户可以拒绝、允许一次或在服务端支持时允许本次对话；决定按 App Server 官方响应结构回传。
- `item/permissions/requestApproval` 的拒绝响应为空权限且仅限当前轮次；允许响应只回传服务端本次明确请求的权限，不自行扩大范围。
- 外部客户端或任务中断使审批失效时，PinChat 应清除对应卡片，不保留无法操作的过期授权。

## 5. 工作目录与文件边界

- PinChat 继续使用独立会话工作目录，工作区读写默认只允许该边界内的修改；读取、写入其他位置或使用网络时按 Codex 沙箱和审批规则处理。
- 用户通过附件明确选择的文件和文件夹继续作为任务上下文发送；选择附件本身不等同于授予任意写权限。
- 完全访问不等同于“扫描全机”。只有用户请求和任务需要时，Codex 才应调用文件或命令工具。
- 对受 macOS 保护的目录，设置页应提供进入“完全磁盘访问权限”系统设置的入口，但 PinChat 不自动修改系统隐私设置。

## 6. 验收与交付

- 自动测试覆盖三个权限档位到官方 App Server 参数的映射、新建与恢复线程参数、命令审批、文件审批和权限扩展响应。
- 验证字符串与数字两类 App Server 请求 ID、允许一次、会话允许和拒绝路径。
- 完成 Swift 测试、Xcode 构建、Release 构建、签名、全部冻结基线哈希校验与本机启动验证。
- 应用版本升级为 0.3.2（构建号 10），更新 README、验证报告、应用包和源码压缩包。
- 终止旧版进程并从完整 Release 路径启动新版；本轮创建本地 Git 提交，不自动推送远端。
